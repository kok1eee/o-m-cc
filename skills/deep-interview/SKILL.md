# Deep Interview - 構造化インタビュー（掘り下げ / grill）

対話で要件・設計を詰めるスキル。フェーズの違う 2 モードを持つ。

> **対話前提スキル**: 1 問ずつの掘り下げが本質なので、AskUserQuestion が使えない環境では「対話モードで /deep-interview を実行してください」と案内して終了する。

## 入力

`$ARGUMENTS`（曖昧なアイデア、または詰めたい plan/design）

## Step 0: モード判定

| 条件 | モード |
|---|---|
| `plan/design.md` / `plan/requirements.md` が存在、または $ARGUMENTS が既存の設計判断を指す、または「詰めて」「grill」「叩いて」「この設計で大丈夫」等の語 | **grill**（→ Mode B） |
| 要件がまだ無い・曖昧なアイデアのみ・「何を作ればいいか」 | **掘り下げ**（→ Mode A） |

判断に迷うときだけ AskUserQuestion で「①ゼロから要件を掘り下げる ②既存 plan を詰問する」を1問確認する。

---

## Mode A: 掘り下げ（elicit）— 要件がまだ無いとき

discovery-council の前段。曖昧なアイデアを 5 軸で言語化する。

### 原則
- **1回に1つの質問**。バッチで聞かない / 前の回答を踏まえて次を決める
- 選択肢を提示する（答えやすくする）/「なぜ？」「たとえば？」「もし○○なら？」で掘り下げる
- 最大 **7問** で打ち切る（ユーザー負担を最小化）

### 5軸の曖昧性評価（ユーザーには見せず内部評価）

| 軸 | 問い |
|----|------|
| **WHO** | 誰のための機能か？ |
| **WHAT** | 何を実現するか？具体的な振る舞いは？ |
| **WHY** | なぜ必要か？現状の課題は？ |
| **SCOPE** | 何を含み、何を含まないか？ |
| **CONSTRAINT** | 技術的制約、期限、依存は？ |

### A1: 初期分析
入力を読み、5軸を [明確 / やや曖昧 / 曖昧] で評価。既存コードがあれば Glob/Grep/Read で精度を上げる。

### A2: インタビューループ
最も曖昧な軸から1問ずつ。必ず 3-4 選択肢 + 自由記述を提示。
- 「分からない」→ 仮定を提案して確認（「○○と仮定してよいですか？」）
- 抽象的 → 具体例を求める / 矛盾 → 優先順位を聞く
- 終了: 全軸 [明確] / 7問到達 / 「もういい」

### A3: 要件サマリー確認
5軸で構造化して最終確認（OK / 修正あり）。

### A4: discovery-council へハンドオフ
```
Skill: discovery-council
Args: <整理された要件サマリー>
```

## Mode B: grill（stress-test）— plan/design が既にあるとき

完成した plan/design を**容赦なく詰問**し、実装前に穴を潰す。`critic`（非対話で一括批判レポートを返す agent）と違い、**1問ずつ対話で決定木を降りる**のが本質。

### 原則
- **1回に1つの質問**。バッチで聞かない
- **決定木を branch ごとに降りる**: 決定を1つずつ解決し、決定間の依存を順番に潰していく
- **各質問に推奨回答を添える**（「私の推奨は X、理由は〜」）。ユーザーが即断できる形にする
- **コードベースで答えが出る質問は、聞かずに自分で Glob/Grep/Read して答える**（無駄な往復を減らす）— これが grill の肝
- 共有理解に達するまで relentless に続ける。ただし「もういい / 十分」で打ち切る

### 観点（決定木の枝）
`facets/references/plan-review-checklist.md` を Read し、4 観点（完全性 / 実現可能性 / リスク管理 / 明確性）を決定木の枝として使う。

### B1: plan の取り込み
$ARGUMENTS / `plan/*.md` / `design.md` を Read。明示・暗黙の**決定点を列挙**する。先に Glob/Grep でコード文脈を埋めておく。

### B2: 詰問ループ
最も未解決・最もリスクの高い決定から1問ずつ:
```yaml
AskUserQuestion:
  question: "<決定点への鋭い問い>（推奨: <推奨案> / 理由: <根拠>）"
  options:
    - "<推奨案（Recommended）>"
    - "<代替案>"
    - "自由に記述"
```
- **コードで判明する事項は質問にしない**。調べて「`<file:line>` を見たら X なのでこの枝は解決」と報告して次へ
- 1つ解決したら、それに依存する下流の決定へ降りる

### B3: 解決サマリー
詰めた決定を構造化して確認。残った**未解決点・リスク**を明記する。

### B4: 反映
- `design.md` があれば、解決した決定の反映（更新）を提案
- 実装へ進むなら sisyphus Phase 4 / 通常実装へ。要件レベルの欠落が出たら **Mode A or discovery-council に戻す**

## Gotchas

- **モード誤判定で空回り**: plan/design.md も具体的な設計記述も無いのに grill に入ると詰問対象が無い。その時は掘り下げ（Mode A）に落とす
- **grill で聞きすぎる**: コードで答えが出る質問を人間に投げると往復が無駄。必ず先に Glob/Grep/Read で self-answer を試みてから AskUserQuestion する
- **critic との混同**: 非対話で一括の批判レポートが欲しいなら `critic` を spawn する。grill は「1問ずつ対話で決定木を降りる」用途。両者は補完関係（同じことを二重にやらない）
- **掘り下げモードで7問超過**: ユーザー負担になる。7問で打ち切り、残りは仮定として明記して discovery-council へ渡す
