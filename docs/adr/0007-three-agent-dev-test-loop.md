# ADR-0007: 実装ループに3エージェント方式（Implementer → Verifier → Debugger）を導入

- Status: accepted
- Date: 2025-03-18

## Context

Sisyphus の実装フェーズで、1つのエージェントが実装・テスト・修正を全て行っていた。同じエージェントが書いたコードを自分で検証すると、確認バイアスにより問題を見落としやすい。実際の開発チームでも「自分のバグは自分で見つけにくい」のは既知の問題。

一方で、全タスクに3エージェントを投入するとトークンコストが過大になる。

## Decision

タスク規模に応じて実行方式を切り替える条件付き3エージェント方式を採用する。

- **S（小規模）**: 1-2ファイルの修正 → 自分で実装 + テスト
- **M-L（中〜大規模）**: 新機能、3ファイル以上 → 3エージェント方式

3エージェントの役割分離：
- **Implementer（自分）**: コードを書く。デバッグはしない
- **Verifier**: adversarial に検証。壊せるか試す。書いた人の「動くはず」を信用しない
- **Debugger**: 先入観なしで根本原因を調査。実際の動作だけを見る

重要な原則: Debugger の修正結果は Implementer ではなく **Verifier に戻す**。修正者の「直した」を信用しない。

## Consequences

- **良い面**: 確認バイアスの排除。実装者・検証者・修正者の役割分離により、それぞれの観点に集中できる。品質が上がる
- **悪い面**: M-L タスクでのトークンコストが増加。小規模プロジェクトでは過剰になりうる。3エージェント間の情報伝達でコンテキストが失われる可能性
