# Plan or Act - タスク複雑度による自動モード切替

**タスクの複雑さに応じて、自動的にplanモードに入る。**

## 判定基準

### そのまま実行（Act）

以下の**すべて**に該当する場合のみ、直接実行する：

- 1-2ファイルの修正で完結する
- 変更箇所が明確（typo修正、変数名変更、単純なバグ修正）
- ユーザーが具体的な指示を出している（「この行をこう変えて」）
- 既存パターンの踏襲（同じ構造のファイル追加など）

**Actの具体例：**
- 「この行のtypo直して」
- 「変数名を camelCase に変えて」
- 「この関数の戻り値を string にして」
- 「README のバージョン番号を更新して」
- 「このファイルに import を追加して」

### 自動でplanモードに入る（Plan）

以下の**いずれか**に該当する場合、自動的に `EnterPlanMode` を実行する：

- 3ファイル以上の変更が見込まれる
- アーキテクチャの判断が必要（どこに置くか、どう設計するか）
- 複数の実装方針がありえる
- 要件が曖昧で調査が必要
- 既存コードへの影響範囲が不明

**Planの具体例：**
- 「〜機能を追加して」「〜できるようにして」— ゴールだけで手段が未定
- 「リファクタして」「設計を見直して」「移行して」— スコープが広い
- 「〜が動かない、直して」— 原因調査が必要なバグ
- 「どうすればいい？」「いい方法ある？」— 相談・方針決め
- 「パフォーマンス改善して」「テスト追加して」— 対象の特定が必要

## 振る舞い

1. ユーザーからタスクを受け取る
2. 上記の判定基準でトリアージする
3. **Act判定** → そのまま実装に着手
4. **Plan判定** → 即座に `EnterPlanMode` を実行

## 注意

- 迷ったらplanモードに入る（手戻りのコストの方が高い）
- planモードで整理してから実装した方が品質が高い
