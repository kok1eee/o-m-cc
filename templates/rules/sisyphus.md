# Sisyphus Mode

**タスク完了まで決して止まらない。**

## 原則

1. **Task First** - 作業開始時に TaskCreate でタスクを登録し依存関係を設定
2. **One at a Time** - 同時に in_progress は1つだけ
3. **Complete Honestly** - 本当に完了したタスクのみ completed に
4. **Never Abandon** - 途中で止まらない
5. **Review Before Done** - 完了前に code-reviewer subagent でレビュー

## 完了条件

全てのTODOが完了し、レビューで Critical がない場合のみ完了。
stop-guard が diff の変更量を検知し、閾値以上なら `/quality-gate` を強制する（`<proof>QUALITY_GATE_PASSED</proof>` が必要）。

## Verification - 証拠なき完了は完了ではない

```
完了を宣言する前に、必ず検証コマンドを実行し、その出力を示せ。
```

### 検証ゲート

タスク完了を宣言する**前に**、以下を実行：

1. **特定**: この完了を証明するコマンドは何か？
2. **実行**: そのコマンドをフルで実行（過去の結果は不可）
3. **確認**: 出力を読み、exit code・失敗数を確認
4. **報告**: 出力を添えて完了を宣言

### 検証の対照表

| 宣言 | 必要な証拠 | 不十分な証拠 |
|------|-----------|-------------|
| テスト通過 | テスト実行出力: 0 failures | 前回の結果、「通るはず」 |
| ビルド成功 | ビルドコマンド: exit 0 | linter通過、ログが良さそう |
| バグ修正 | 再現テスト: pass | コード変更した、直ったはず |
| 要件充足 | 要件を1行ずつチェック | テストが通った |

### Red Flags — こう思ったら止まれ

以下のいずれかを考えていたら、**検証が足りていない**：

- 「たぶん動くはず」
- 「さっき通ったから大丈夫」
- 「シンプルだからテスト不要」
- 「コード見れば正しいのは明らか」
- 「あとで確認する」
- 「手動で確認した」（自動テストがある場合）

### 言い訳 vs 現実

| 言い訳 | 現実 |
|--------|------|
| 「動くはず」 | 検証コマンドを実行せよ |
| 「自信がある」 | 自信 ≠ 証拠 |
| 「今回だけ」 | 例外なし |
| 「linter通った」 | linter ≠ テスト ≠ ビルド |
| 「疲れた」 | 疲労は免罪符ではない |

## 禁止事項

- 途中放棄禁止 - TODOが残っている状態で「完了」と言わない
- レビュースキップ禁止 - 完了前に必ずレビュー
- 検証スキップ禁止 - 証拠なき完了宣言は禁止

## Bash 使用制限

以下のコマンドは **禁止**（専用ツールを使用）:

| 禁止コマンド | 代替ツール |
|-------------|-----------|
| `find` | Glob ツール |
| `grep` / `rg` | Grep ツール |
| `cat` / `head` / `tail` | Read ツール |
| `ls | grep` | Glob ツール |

**許可される Bash**:
- `jj` / `git` - バージョン管理
- `npm` / `uv` / `pip` - パッケージ管理
- ビルド/テストコマンド

## コード品質基準

| 項目 | 基準 | 理由 |
|------|------|------|
| ファイルサイズ | 200-400行推奨、800行上限 | 可読性と保守性 |
| 関数サイズ | 50行以下 | 単一責任の原則 |
| ネスト深度 | 4段以下 | 複雑性の制御 |
| 引数の数 | 3個以下（多い場合はオブジェクト化） | 理解しやすさ |

**イミュータビリティ優先**:
- 既存オブジェクトを変更しない
- 常に新しいオブジェクトを作成して返す
- 副作用を最小限に

**命名規則**:
- 変数名は意図を表す（`d` → `currentDate`）
- 関数名は動詞で始める（`getUser`, `validateInput`）
- 略語を避ける（`btn` → `button`）
